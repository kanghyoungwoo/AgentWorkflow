# M4-r1 작업 지시서 — 순차 파이프라인, run/resume, 샘플 앱

## 목표
순차 모드(`--parallel` 없음)의 전체 파이프라인을 만든다: SETUP → PLANNING → (plan 모드면 끝) → main 레인 DEV → QA → (FAIL이면 FIX_PLANNING → DEV → QA) → WIKI → DONE, 그리고 wiki 단독 모드와 resume. M3의 `invoke`, `runReviewLoop`, gates, `decideQa`를 그대로 사용한다. 병렬 레인·MERGE·통합 QA는 M6, codex 어댑터는 M5, 예약(at)·status/logs/list/watch/cleanup은 M7이다.

## 따를 spec 절
§2.1, §2.3, §2.4, §4.1~§4.3, §5 전체(입력 표 포함), §5.8, §6.1, §6.3 끝 문단(cwd), §6.4, §7, §8 전체(§8.5 포함), §9.1 run·resume 행, §10.1~§10.8(프롬프트 본문), §11.

### `src/engine/pipeline.ts` — 순차 상태 기계
- `runPipeline(runDir, deps)`: state.json을 읽고, 진행할 수 있는 일을 끝까지 하거나 멈춘 뒤 종료 코드를 돌려준다. `deps`는 테스트 주입용으로 `{ clientFor(config, role): AgentClient, appRunner, now }`를 받는다.
- 매 단계가 끝날 때마다 state.json을 쓰고 이벤트를 남긴다(§4.3의 type). 이벤트의 lane, stage, role을 채운다(review-loop의 emit을 감싸 lane, stage, role을 넣는다).
- **SETUP**(§2.4, §4.2): `setupDone`이 false면 setupCommand를 런 worktree에서 `spawnProcess(sh -c)`로 실행한다. 실패하면 Pending `environment`(stage SETUP, 로그 끝 200줄).
- **PLANNING**: 초기 모드 루프. 게이트는 G1(병렬 아님). 승인되면 `01-planning/plan.json`과 `plan.md`를 쓰고(순차: todo lane `main`, 시나리오 lane null), lane `main` LaneState를 만든다(branch·worktree는 런 것, portSlot 0, setupDone true). 파일은 `round-NN.{author,gate,review}.json`에 남긴다.
  - plan 모드면 DONE, 종료 코드 0이다. `resume --mode full`이면 mode를 full로 바꾸고 이어 간다.
- **DEV**: 대상 = lane `main`의 `approved=false` 항목, `stageBase` = 루프 시작 HEAD. 작성자 `afterAttempt`에서 `commitAll`(§2.4 WIP 메시지)한다. 작성 출력이 오면 plan.json의 checked·evidence를 갱신한다. 게이트는 G3, G4, G5 순서로 모두 실행한다(G5 로그 `round-NN.tests.log`). 승인되면 squash 커밋(`aw(<run-id>): main DEV 승인 (<ids>)`)을 하고 approved=true로 바꾸며 todo.md를 갱신한다(§4.3 형식). fix 뒤 DEV 파일은 `fix-<N>/`에 둔다.
- **QA**: attempt 번호 증가, qaDir = `03-qa/main/attempt-NN/`(scripts·evidence 디렉터리 생성).
  - 실행할 시나리오가 0개면 skipped다.
  - app이 있으면 포트를 확인하고 앱을 띄운다. 기동에 실패하면 자동 결함 `BUG-APP-START`로 report.json·md를 쓴다.
  - browser 시나리오가 있는데 chromium이 없으면 environment다.
  - QA 호출(`guardDir` = worktree, `check` = G9)이 끝나면 앱을 종료하고 report.json·report.md를 쓴다.
  - `decideQa`로 다음 단계를 정한다. fix면 phase FIX_PLANNING, 새 루프.
- **FIX_PLANNING**: fix 모드 루프. 입력은 승인된 plan과 마지막 attempt의 defects이고, 게이트는 G1 fix 모드다. 승인되면 FIX·QA id를 다음 빈 번호로 다시 매긴다(`renumber` 이벤트). lane `main`으로 todos에 붙이고 시나리오 lane은 null로 둔다. 그 뒤 DEV(fix-N)로 간다.
- **WIKI**: stageBase = 런 worktree HEAD. 변경 파일은 `diffNameOnly(sinceRef ?? baseRef)`에서 wikiDir을 뺀 것이다. 게이트는 G8. 작성자 afterAttempt에서 WIP 커밋한다. 승인되면 squash(`aw(<run-id>): run WIKI 승인`)하고 DONE, 종료 코드 0이다.
- **wiki 모드**: SETUP → WIKI만. 요청이 없으면 "(요청 없음)", plan이 없으면 "(계획 없음)".
- **멈춤**: 루프나 QA가 pending을 내면 Pending(id `P-NNN`, lane, stage, createdAt)을 추가하고 PAUSED로 바꾼다. 종료 코드는 우선순위 1 > 21 > 20 > 22로 정하고 `lastExitCode`에 남긴다.
- `--parallel` 런은 이번 마일스톤에서 `run`이 "M6에서 지원" 오류와 함께 종료 코드 2를 낸다.

### `src/commands/run.ts` — `run`, `resume` 핸들러 (§9.1, §8.5)
- **run**:
  1. 요청·설정을 검증하고(실패 2), `HEAD`(wiki면 `--since`도)를 해석하고, run-id를 만든다.
  2. `initRunDir`, `acquireLock`, `addExcludes(['/ai-log/', '/.aw/'])`, `worktreeAdd(.aw/worktrees/<run-id>/main, aw/<run-id>, HEAD)`, state 작성, `run_start` 이벤트.
  3. run-id를 첫 줄에 출력하고, 이후 이벤트를 한 줄씩 stdout에 출력한다.
  4. 끝나면 lock을 해제한다.
- **resume**: §8.5 공통 절차와 표를 따른다(merge_conflict는 M6, at 예약 해제는 M7이므로 지금은 `scheduledResume`만 null로 둔다).
  - `--answer`는 loop pending이면 `applyAnswer`, QA pending(qa_rollback_cap, environment)이면 레인 decisions에 추가한다. qa_rollback_cap이면 `qaRollbacks`를 0으로 하고 QA부터 다시 한다.
  - `--grant`는 DEV·WIKI 루프에만 쓴다.
  - 인자가 없으면 failed와 rate_limited를 재시도한다. 비정상 종료(RUNNING인데 lock PID가 죽음)도 이어 간다. 재개 전에 worktree를 `restore(HEAD)`로 정리한다.
  - `--mode full`은 plan 모드 런을 이어 간다.
- **SIGINT/SIGTERM**: `killAllChildren()`을 호출하고, 진행 중 단계에 Pending `failed`를 남긴 뒤 종료 코드 1, lock을 해제한다(§8.3).
- `src/cli.ts`에 run·resume 핸들러를 등록한다.
