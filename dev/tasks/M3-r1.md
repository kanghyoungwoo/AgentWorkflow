# M3-r1 작업 지시서 — 검수 루프와 게이트 G1~G9

## 목표
작업↔검수 공통 루프, 호출 재시도(§6.1), 출력 스키마 5종, 기계 게이트 G1~G9, QA 결과 판정을 만든다. 프롬프트 조립(stages.ts), 파이프라인, 앱 기동, 레인·머지는 M4·M6이다. 이번 모듈은 그 부분을 **콜백으로 주입받아** fake-client만으로 테스트할 수 있어야 한다.

## 따를 spec 절
§2.4(커밋·G6 정리), §5.2~§5.7(출력 타입과 일관성 검사 §5.4), §5.8 LoopState·Pending, §6.1(재시도 규칙), §6.4(한도 → Pending), §7 전체, §8.1, §8.2, §8.5 중 루프 상태 규칙, §11.

## 만들 파일

### `schemas/*.schema.json` (§5 서두, §3)
`plan-author`, `review`, `dev-author`, `qa-report`, `wiki-author` 5종. draft-07, **Codex strict 규칙**을 따른다. 즉 모든 객체가 `additionalProperties: false`이고 모든 속성이 `required`이며, null 가능 값은 `type: [..., "null"]` 또는 `anyOf`로 표현한다. enum은 §5와 1:1로 맞춘다. 개수 조건(1개 이상 등)은 스키마가 아니라 코드(게이트·일관성 검사)에서 본다.

### `src/engine/invoke.ts` — 재시도가 들어간 호출 (§6.1, §6.4, §7 G6)
```ts
type InvokeOptions = {
  client: AgentClient;
  makeCall: (attempt: 1 | 2, previousError: string | null) => Promise<AgentCall>; // 2회차에는 오류를 프롬프트에 붙이는 건 호출자 몫
  schemaName: "plan-author" | "review" | "dev-author" | "qa-report" | "wiki-author";
  guardDir: string | null;   // 읽기 전용 호출이면 G6을 검사할 worktree, 작성 호출이면 null
  check?: (output) => Promise<string | null>;  // 추가 검증(G9 등). 문자열이면 형식 오류로 취급
  afterAttempt?: (result: AgentResult) => Promise<void>;  // dev/wiki의 WIP 커밋 등(성공·실패 무관하게 매 시도 후)
};
type InvokeOutcome =
  | { kind: "ok"; output: T }
  | { kind: "failed"; detail: string }                  // 2회 모두 실패
  | { kind: "rate_limited"; resetAt: string | null; detail: string };
```
- 시도마다 다음 순서로 처리한다.
  1. `guardDir`가 있으면 호출 전에 `restore(guardDir, "HEAD")`로 정리하고 HEAD를 기록한다.
  2. 호출한다.
  3. `afterAttempt`를 실행한다.
  4. 한도면 즉시 `rate_limited`로 끝낸다(재시도 없음).
  5. 아래를 차례로 검사하고, 하나라도 실패하면 그 시도를 실패로 본다.
     - 프로세스 오류(exitCode≠0, 타임아웃, error)
     - ajv 스키마 검증
     - §5.4 일관성 검사
     - `check`
     - G6(`guardDir`가 있으면: status가 비었고 HEAD가 그대로인지)
     - G6을 위반하면 기록한 HEAD로 `restore`한다.
- 실패 이유는 다음 시도의 `makeCall`에 넘긴다. 2회 모두 실패하면 `failed`이고, detail에는 두 시도의 이유를 모두 적는다.
- 스키마 로드와 ajv 컴파일은 모듈 수준에서 한 번만 한다.

### `src/engine/gates.ts` (§7)
게이트마다 export 함수 하나. 실패하면 `Issue`(id `GATE-<코드>`, target `"general"`, problem에 문제를 모두 나열, requiredChange)를, 통과하면 `null`을 돌려준다. 메시지는 한국어로 쓴다.
- `gateReq(output, { mode: "initial"|"fix", reqIds, hasApp, parallel, plan: Plan | null, defectIds })` — G1의 초기 모드·fix 모드 규칙 전부.
- `gateLanes(output, { maxLanes })` — G2(parallel 초기 모드에서만 호출).
- `lanesOverlap(lanes)` → boolean — G2' 판정(앞 `./`·끝 `/` 제거, 경로 구성요소 단위 접두사, 레인 1개면 true).
- `gateItems(output, targetIds)` — G3.
- `gateEvidence(output, { cwd, stageBase })` — G4(파일 존재 + 1개 이상이 `diffNameOnly(stageBase)`에 포함).
- `gateTests({ cwd, testCommand, timeoutMs, logPath })` — G5. `sh -c`로 실행하고 로그를 logPath에 남긴다. 실패하면 problem에 로그 끝 200줄. testCommand가 null이면 null.
- `gateOwned({ cwd, stageBase, ownedPaths })` — G7.
- `gateWikiScope(output, { cwd, stageBase, wikiDir })` — G8.
- `gateQaReport(report, { scenarioIds, qaDir })` → 오류 문자열 | null — G9(evidence 경로가 qaDir 밖으로 나가지 않고 존재하는지 포함). invoke의 `check`로 쓴다.

### `src/engine/review-loop.ts` (§8.1)
```ts
type LoopHooks<A> = {
  author: (loop: LoopState) => Promise<InvokeOutcome<A>>;          // 프롬프트·커밋은 호출자 몫
  gates: (output: A, loop: LoopState) => Promise<Issue[]>;          // 실패한 게이트 Issue 목록
  review: (output: A, loop: LoopState) => Promise<InvokeOutcome<ReviewOutput>>;
  emit: (event: Omit<RunEvent, "at">) => Promise<void>;
};
type LoopResult<A> =
  | { kind: "approved"; output: A }
  | { kind: "paused"; pending: Omit<Pending, "id" | "createdAt" | "lane" | "stage"> };
runReviewLoop<A extends { status: string; blocker: Blocker | null }>(loop, limits, hooks): Promise<LoopResult<A>>
```
- §8.1 절차와 표의 모든 행을 구현한다.
  - 라운드 시작 시 `round += 1`.
  - 작업 결과가 failed나 rate_limited면 Pending(`failed` 1, `rate_limited` 22, resetAt 포함).
  - 작업이 BLOCKED면 `permission_full`은 21, 그 외 kind는 20.
  - 게이트 실패나 REJECTED면 반려로 처리한다(`judgedRounds += 1`, `lastOutput`·`lastIssues` 갱신).
  - `reviewIssues` 갱신: 검수 반려면 검수 지적으로 교체하고, 게이트 반려면 게이트 지적을 덧붙인다(같은 GATE id는 교체).
  - issueStreak: 이번 반려에 나온 id는 +1, 나오지 않은 id는 삭제(0).
  - 판정 순서: `loop_repeat`(sameIssueLimit 도달) → `round_cap`(judgedRounds ≥ maxReviewRounds) → 다음 라운드.
  - 검수 BLOCKED면 `reviewer_blocked` 20.
  - 검수 failed나 rate_limited는 작업과 같은 방식으로 처리한다.
- 중단된 라운드(failed, rate_limited, BLOCKED)는 judgedRounds와 lastOutput을 바꾸지 않는다.
- 이벤트(§4.3 type: `author`·`gate`·`review`·`pause`)를 emit하고, Pending의 summary·detail은 한국어로 채운다.
- `applyAnswer(loop, answer)`, `applyGrant(loop, grant)`를 만든다(§8.1 마지막 문단, §8.5 표 1행). judgedRounds·issueStreak 리셋, decisions 추가.

### `src/engine/qa.ts` (§8.2) — 판정만
- `decideQa(lane: LaneState, outcome, limits)`: outcome은 `{ kind: "report", report }`, `{ kind: "skipped" }`, `{ kind: "auto_fail", defect }`, `{ kind: "failed", detail }`, `{ kind: "rate_limited", ... }`, `{ kind: "environment", detail }` 중 하나다. 다음 행동을 돌려준다.
  - `{ next: "done" }`
  - `{ next: "fix", defects }`: `qaRollbacks += 1` 포함
  - `{ next: "paused", pending }`: 표의 각 행에 따라 `qa_rollback_cap` 20, `environment` 20, `failed` 1, `rate_limited` 22
- QA BLOCKED 리포트도 `environment`로 처리한다.
- 앱 기동과 QA 호출 자체는 M4에서 만든다.
