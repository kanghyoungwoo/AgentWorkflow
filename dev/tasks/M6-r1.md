# M6-r1 작업 지시서 — 병렬 레인, MERGE, 통합 QA

## 목표
`--parallel` 런을 지원한다. 순서는 기획(레인 분할 포함) → G2' 판정(겹치면 순차로 전환) → 레인별 worktree에서 DEV/QA/FIX를 **동시에** 실행 → 모든 레인 PASS → MERGE → INTEGRATION_QA(⟲ integration fix) → WIKI다. 순차 모드 동작은 바꾸지 않는다(기존 테스트 전부 유지). 예약·조회 명령·cleanup은 M7이다.

## 따를 spec 절
§2.2, §2.4(레인 시작, MERGE 행), §4.3(레인별 경로, `fix/<lane>-<N>`, `03-qa/<lane|integration>/`), §5.3(parallel 기획, lanes, fix 붙이기와 재번호), §5.6(레인 시나리오, 포트 슬롯 a=1…), §5.8(LaneState, integration), §7 G2·G2'·G7, §8.2(통합 testCommand 실패 → BUG-INTEGRATION-TESTS), §8.3, §8.5(merge_conflict, `--lane`), §9.1 run·resume, §11.

## 바꿀 것

### 1. 레인별 문맥으로 리팩터링 (`src/engine/pipeline.ts`)
- `activeLane`, `activeStage`, `activeRole`, `fixNumber` 같은 클로저 공용 변수는 레인이 동시에 돌면 서로 덮어쓴다. 레인·단계·역할·fix 번호를 담은 **레인 문맥 객체**를 함수 인자로 넘기도록 바꾼다(이벤트, Pending, raw 경로, cwd가 모두 이것을 쓴다).
- 공유 자원은 직렬화한다. 대상은 state.json 쓰기, plan.json·plan.md 갱신과 재번호, Pending id 할당이다. 단순한 promise 큐(뮤텍스) 하나면 충분하다.
- fix 번호는 레인마다 `01-planning/fix/<lane>-<N>`의 기존 디렉터리로 정한다(지금 main에 하는 방식을 레인별로 일반화). todo.md는 `02-development/<lane>/todo.md`다.
- 재번호 이벤트는 id가 실제로 바뀐 경우에만 남긴다(M5 참고 사항).

### 2. 병렬 기획과 G2/G2'
- parallel 런의 PLANNING Run context는 `parallel: true`이고, 게이트는 G1(parallel=true)과 G2다.
- 승인되면 `lanesOverlap`으로 판정한다.
  - **겹치거나 레인이 1개**: `mode_switch` 이벤트를 남기고 순차와 똑같이 진행한다(todo lane `main`, 시나리오 lane null, plan.lanes null).
  - **겹치지 않음**: plan.lanes를 유지하고, 레인마다 LaneState를 만든다.
    - id: a..
    - branch: `aw/<run-id>-lane-<id>`
    - worktree: `<ws>/.aw/worktrees/<run-id>/lane-<id>`
    - ownedPaths: 기획의 값
    - portSlot: 레인 순서 기준 1부터
    - setupDone: false
    - phase: DEV
  - stage는 `LANES`다.

### 3. 레인 동시 실행
- LANES 단계에서 ACTIVE 레인을 모두 동시에 실행한다(`Promise.all`, 레인 수는 이미 maxLanes 이하).
- 각 레인은 다음 순서로 진행한다.
  1. 레인 시작 시 worktree·브랜치를 만들고(이미 있으면 건너뜀) `setupCommand`를 실행한다. 실패하면 그 레인에 Pending `environment`(stage SETUP)를 남긴다.
  2. DEV: 게이트는 G3, G4, G5, **G7(ownedPaths)** 순서다. Run context의 ownedPaths·interfaces는 그 레인의 값이다. 리뷰 입력의 ownedPaths도 같다.
  3. QA: lane이 그 레인인 시나리오만 실행하고, 포트는 그 레인의 슬롯이다.
  4. FIX: 붙이는 항목의 lane은 그 레인, 새 시나리오의 lane도 그 레인이다.
- 한 레인이 멈춰도 다른 레인은 끝나거나 멈출 때까지 진행한다(§2.2).
- 모든 레인이 DONE이면 MERGE로 간다. 하나라도 PAUSED면 PAUSED로 끝내고, 종료 코드는 우선순위 규칙을 따른다.

### 4. MERGE (§2.4, §8.5)
- 런 worktree에서 레인 id 순서대로 `merge(runWorktree, branch)`를 한다. `isAncestor(branch, HEAD)`면 건너뛴다. 머지할 때마다 `merge` 이벤트를 남긴다.
- 충돌이 나면 Pending `merge_conflict`(lane null, stage MERGE, 20)를 남긴다. detail에는 런 worktree 경로, 충돌 파일, 다시 실행할 명령 `git -C <runWorktree> merge --no-ff aw/<run-id>-lane-<id>`를 넣는다.
- resume(`--answer`)하면 MERGE를 이어서 진행한다.

### 5. INTEGRATION_QA (§2.2, §8.2)
- `state.integration` = LaneState(id `integration`, 런 branch·worktree, portSlot 0, setupDone true, phase QA).
- QA attempt마다 testCommand가 있으면 먼저 런 worktree에서 실행해 `03-qa/integration/attempt-NN/evidence/integration-tests.log`에 남긴다. 실패하면 QA를 호출하지 않고 자동 결함 `BUG-INTEGRATION-TESTS`로 FAIL 처리한다(report.json·md 작성).
- 통과하면 **전체 시나리오**로 QA한다.
- FAIL이면 integration 레인에서 FIX_PLANNING → DEV를 한다. G7은 없고, 파일 위치는 `fix/integration-N`, `02-development/integration/fix-N`이다. 그 뒤 다시 INTEGRATION_QA를 한다.
- PASS면 WIKI로 간다.

### 6. 명령 (`src/commands/run.ts`)
- `run --parallel`을 허용한다(state.parallel = true). 지금의 "M6에서 지원" 오류는 없앤다.
- resume:
  - Pending이 여러 레인에 있으면 `--lane`으로 고른다. integration QA Pending은 레인 decisions(integration)에 넣는다.
  - merge_conflict는 `--answer`로 지운다(답변은 resume 이벤트에만 남김).
  - 병렬 레인 worktree도 재개 전에 `restore(HEAD)`한다.

## 테스트 (fake-client, 임시 git 저장소, 오프라인)
- 레인이 겹치면(`src`와 `src/a`) 순차로 전환한다(`mode_switch` 이벤트, plan.lanes null, todo lane main).
- 2레인 정상 완주:
  - 두 레인의 DEV 호출이 **동시에 진행 중**인 순간이 있어야 한다. fake-client에서 두 호출이 모두 들어올 때까지 기다리는 장벽으로 확인한다.
  - 레인 브랜치·worktree가 생성된다.
  - 런 브랜치에 merge 커밋 2개가 남는다.
  - 통합 QA는 전체 시나리오로 실행된다.
  - WIKI를 거쳐 종료 코드 0으로 끝난다.
  - 레인별 todo.md와 `03-qa/a`, `03-qa/b`, `03-qa/integration`이 생긴다.
- 레인 a가 BLOCKED(20)여도 레인 b는 DONE까지 간다. 종료 코드는 20이고, `resume --lane a --answer`로 끝까지 간다.
- G7: 레인 a가 ownedPaths 밖 파일을 바꾸면 `GATE-OWNED`로 반려된다.
- 머지 충돌: Pending merge_conflict이 생기고 detail에 명령이 들어간다. 테스트가 그 명령을 실행해 충돌을 해결하고 커밋한 뒤 resume하면 남은 레인을 머지하고 완주한다.
- 통합 testCommand 실패: BUG-INTEGRATION-TESTS가 생기고, integration fix(FIX lane `integration`, fix 디렉터리)를 거쳐 통과한다.
- 통합 QA FAIL: integration fix를 거쳐 PASS하고 WIKI로 간다.
- 공유 자원: 두 레인이 동시에 fix를 승인해도 FIX id가 겹치지 않는다(재번호).
- 순차 모드 기존 테스트는 모두 그대로 통과해야 한다.
